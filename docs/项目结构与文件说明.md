## 一、先看全局：跑起来是哪几个进程

```
┌──────────────────────────────────────────────────────────────┐
│ 进程 1：streamlit run app/ui.py        端口 8501  ← 人看的界面 │
│ 进程 2：uvicorn app.main:app            端口 8000  ← 给系统集成 │
│ 进程 3：ollama serve                   端口 11434 ← 本地大模型 │
└──────────────────────────────────────────────────────────────┘
        ↓ 三者都是独立进程，通过本地 HTTP 互相说话
   ui.py / main.py  ──HTTP──→  localhost:11434  (Ollama 生成)
   ui.py / main.py  ──函数调用──→  rag.py  (检索、闸门、组装提示词)
```

关键点：**没有数据库服务、没有向量库服务、没有 Redis**。除了 Ollama，全部跑在一个 Python 进程里，索引是磁盘上的两个文件（json + npy）。这是刻意的——政企客户现场部署时，装的东西越少，验收越容易过。

## 三、七个 Python 文件，逐个说清

### 1. `config.py` — 参数总控（61 行，没有任何逻辑）

**为什么单独一个文件**：所有"可以调的数字"集中在一处。客户现场要改切分粒度、要换模型、要调阈值，只改这一个文件，不碰业务代码。

| 参数 | 值 | 调它会发生什么 |
|---|---|---|
| `LLM_MODEL` | `minicpm-v` | 换模型（也可用 `LLM_MODEL=qwen2.5:7b` 环境变量覆盖） |
| `LLM_KEEP_ALIVE` | `60m` | 模型在内存里驻留多久。设短了 → 每次冷启动多等 40 秒 |
| `EMBED_MODEL` | `BAAI/bge-small-zh-v1.5` | 换 embedding 模型（换完必须重建索引，向量维度会变） |
| `CHUNK_SIZE` | `300` | 切片目标长度。调大 → 一条法规被合并，引用定位模糊 |
| `TOP_K` | `3` | 送进提示词的条款数。调到 5 → 首字延迟从 15 秒涨到 28 秒 |
| `CONF_HIGH` / `CONF_LOW` | `0.62` / `0.52` | 置信度三档分界。调高 → 更多问题被拒答 |
| `MAX_TOKENS` | `320` | 回答长度上限。调大 → 小模型开始说空话 |
| `SCENARIOS` | `["制度文件","运维手册"]` | 场景名 = `data/docs` 下的子目录名 |

> `CONF_HIGH/LOW` 为什么是 0.62/0.52 而不是别的数：见技术原理详解 7.1，是在本项目真实语料上跑 benchmark 得出的（正例 cos 0.49~0.84，负例 0.43~0.59）。

### 2. `ingest.py` — 离线建库（309 行，只在建库时跑）

**职责**：把 `data/docs/` 里的文档变成可检索的向量索引。**跑一次即可**，文档变了才重跑。

执行流程（对应函数）：

```
load_documents()      读文件（txt/md/pdf/docx 四种解析器）
   ↓                 + parse_filename() 从文件名解析出版本号
chunk_documents()     切分（三套策略，见下）
   ↓                 + 打元数据：source/version/page/scenario/chunk_id
embed_texts()         向量化（bge-small-zh，512 维，L2 归一化）
   ↓
build_index()         落盘：chunks.json + vectors.npy + meta.json
```

**三套切分策略，按文档形态自动分流**（这是全项目最关键的 100 行）：

| 文档形态 | 用什么函数 | 为什么 |
|---|---|---|
| 法规条款（`第X条` 开头） | `_split_articles()` | 条文是完整规范单元，拦腰截断会产生"半条"，检索到了也答不全 |
| 报错对照表（含 `｜` 竖线） | `_table_chunks()` | 一行一条报错，合并成大块会把 20 条报错的语义搅在一起 |
| 超长条款（>2×CHUNK_SIZE） | `_split_long()` | 极少数条款上千字，按分号切 |

`get_model()` 里有一个**双重检查锁**——因为界面预热线程和用户提问可能同时触发 embedding 加载，没锁会重复装载一份模型（95MB × 2）。

### 3. `rag.py` — 在线问答核心（499 行，被 UI 和 API 共用）

**职责**：拿到问题后，检索→判断能不能答→组装提示词→调模型→返回结构化结果。文件内分五段，从上往下就是一个请求的生命周期：

| 段 | 函数 | 干什么 |
|---|---|---|
| **索引** | `load_index()` / `knowledge_stats()` | 读磁盘索引，进程内缓存（只读一次） |
| **检索** | `_encode_query()` / `search()` / `retrieve()` | 混合检索：语义余弦 0.6 + 字面二元组重合 0.4 |
| **版本** | `is_version_question()` / `keep_latest_versions()` / `version_article_diff()` | 识别版本对比题、去重只留最新生效版、**用代码做条款 diff**（不靠模型推理） |
| **闸门** | `grade_confidence()` / `article_ref_missing()` / `llm_says_cannot_answer()` | 三道拒答闸，见下 |
| **生成** | `warmup_llm()` / `ask_llm()` / `answer()` | 调 Ollama `/api/chat`，`answer()` 是总入口 |

**三道拒答闸的作用顺序**（`answer()` 里 20 行代码，是全项目的灵魂）：

```
闸一 grade_confidence()      纯语义余弦 < 0.52 → 拒答（便宜，先筛掉明显无关）
闸二 article_ref_missing()   问题点名"第 200 条"但检索结果里没这条 → 拒答（结构化校验）
闸三 llm_says_cannot_answer() 模型读完资料说自己答不了 → 拒答 + 二次确认
                             ↑ 二次确认：换个"没有拒答出口"的提示词重问，
                               能抽出答案 = 第一遍误拒（降一档置信度），抽不出 = 真拒答
```

> 为什么一个阈值不够、为什么要二次确认（小模型会误拒）：见技术原理详解 7.1 / 8.1。

**`search()` 里两个容易忽略的细节**：
- 排序用**融合分**（语义+字面），判档用**纯语义分**——两者混用会把"含领域词但答不了"的问题判成依据充分
- 向量已 L2 归一化，所以 `vectors @ qvec` 点积直接就是余弦相似度，不需要再算模长

### 4. `main.py` — HTTP 接口（91 行）

给"系统集成"场景用的。UI 是给人看的，这里是给别的系统调的。

| 端点 | 方法 | 用途 |
|---|---|---|
| `/health` | GET | 健康检查，返回 `{"status":"ok","chunks":287}`——运维探活用 |
| `/stats` | GET | 知识库规模（切片数、维度、语料清单） |
| `/ask` | POST | 问答主接口，入参 `{question, scenario}`，出参含 answer/confidence/citations |
| `/ingest` | POST | 触发重建索引（客户上传新制度后调） |

`lifespan` 里做了启动预热：服务起来就加载索引和 embedding，第一个请求不用等。

> 为什么既做 UI 又做 API：售前演示用 UI（直观），交付联调用 API（可嵌入客户的门户/OA）。这两个诉求在政企项目里通常同时存在。

### 5. `ui.py` — Streamlit 界面（138 行）

**结构就三块**：侧边栏（知识库规模 + 场景切换 + 示例问题按钮）、对话流、每条回答的渲染。

两个值得说的设计：

- **`render_answer()`**：置信度用彩色标签（绿/黄/红）+ 最高相似度数值 + 可展开的"依据条款"（文件名·版本·页码·命中度·原文）。客户验收时第一句话通常是"你凭什么这么答"——这个展开框就是答案。
- **预热逻辑**（页面打开即执行）：后台线程同时加载 embedding 和 LLM 并 `keep_alive`。**页面本身秒开**，不受加载影响。这是 43 秒→6 秒那次修复的产物。

### 6. `benchmark.py` — POC 测试与报告生成（225 行）

**职责**：把"售前做 POC 要手工整理 Excel"这件事变成一条命令。

| 函数 | 干什么 |
|---|---|
| `run_case()` | 跑单条用例，判定通过/未过，记录时延与命中率 |
| `hit_ratio()` | 答案里出现了多少期望特征词（判分前先去空白，防"30 分钟"vs"30分钟"的假阴性） |
| `summarize()` | 汇总：通过率、答案命中率、拒答正确率、平均/P95 时延 |
| `build_report()` | 生成 Markdown 报告（客户视角：指标表 + 逐条明细 + 未通过归因 + 数据不出域声明） |

两种模式，**输出到不同文件**（曾经的 bug：都写同一个文件，快速自检会把正式报告冲掉）：

```bash
python -m app.benchmark            # 完整模式（需模型）→ reports/POC测试报告.md
python -m app.benchmark --no-llm   # 仅检索（500ms 跑完）→ reports/POC测试报告_检索层.md
```

### 7. `qa_set.json` — 24 条测试用例

四类配比是刻意的：常规 10 / 版本对比 4 / 操作辅助 4 / **应拒答 6（占 1/4）**。

应拒答题占比高，是因为**客户验收时必拿"不存在的条款"来考你**（"预算法第 200 条怎么规定的？"）。答错一次，整个 POC 的可信度就没了。这类题在普通 RAG demo 里几乎没人测。

## 四、一次提问，代码是怎么走的

以界面上点「预备费按什么比例设置」为例：

```
① ui.py 捕获问题
       ↓
② rag.answer(question)                          [rag.py:432]
   ├─ on_stage("检索制度条款…")  → 界面显示阶段进度
   ├─ retrieve()                                [rag.py:207]
   │    ├─ _encode_query()  问题 → 512 维向量
   │    ├─ search()         余弦 + 字面融合排序，取 top-3
   │    └─ keep_latest_versions()  同一条款多版本 → 只留最新
   ├─ grade_confidence()    cos=0.805 ≥ 0.62 → "依据充分"（闸一通过）
   ├─ article_ref_missing() 问题没点名条款号 → 跳过（闸二通过）
   ├─ version_article_diff() 非版本题 → 返回空
   ├─ on_stage("本地模型生成回答中…")
   └─ ask_llm()                                 [rag.py:397]
        ├─ _build_context(hits)   3 条条款原文拼成【参考资料】
        └─ POST localhost:11434/api/chat  (keep_alive=60m)
                                           ↓
③ ollama 进程：minicpm-v 推理 → 返回文本
       ↓
④ rag.answer 返回 {answer, confidence, citations, top_score}
       ↓
⑤ ui.render_answer() 渲染：彩色标签 + 正文 + 可展开依据条款
```

**如果走的是拒答路径**：② 里任一闸命中就直接返回，**不调用模型**（省 6-10 秒）。实测 R03/R04/R05 三条拒答题只花 22-102ms，就是这个原因——闸一/闸二在模型之前就拦住了。

## 五、模型文件到底在哪（你问的第一个问题）

### 5.1 两个模型的实际规格

| | `minicpm-v`（主测模型） | `minicpm5-2b`（低配备选） |
|---|---|---|
| 基座架构 | qwen2 + CLIP 视觉编码器 | llama（GGUF 转换） |
| **参数量** | **7.6B**（+ 503.97M 视觉投影层） | **2.5B** |
| 量化 | Q4_0 | Q4_K_M |
| 上下文长度 | 32768 | 131072 |
| 向量维度 | 3584 | 2048 |
| 能力标签 | completion / **vision** | completion / tools / **thinking** |
| 磁盘占用 | 5.5 GB | 1.6 GB |
| 本项目角色 | **POC 实测用这个**（条款复述完整度明显好于 2B） | 低配办公本方案（16GB 机器更宽裕） |

> 注意：README 早期写"8B"是约数，准确是 **7.6B**。对外表述建议用 7.6B。

### 5.2 文件位置（都在你的用户目录下，不在项目里）

```
~/.ollama/                                   总计 8.0 GB
├── models/                                  6.6 GB  ← Ollama 的模型库
│   ├── blobs/                               28 个文件，6.6 GB
│   │   ├── sha256-xxxx...                   模型权重/配置/模板，按内容哈希命名
│   │   │                                    （同一个 blob 被多个模型共享时只存一份）
│   ├── manifests/                           "模型名 → 用哪些 blob" 的清单
│   │   └── registry.ollama.ai/library/
│   │       ├── minicpm-v/latest             5.5 GB 模型的清单
│   │       └── minicpm5-2b/latest           1.6 GB 模型的清单
│   ├── manifests-v2/                        新版 Ollama 的清单结构
│   └── metadata/                            元数据缓存
│
└── gguf/                                    1.4 GB  ← 你自己下载的 GGUF 源文件
    └── MiniCPM5-2B-Q4_K_M.gguf              用 ollama create 导入 2B 模型时用的原料
```

三层关系说清楚：

1. **`~/.ollama/gguf/MiniCPM5-2B-Q4_K_M.gguf`** 是从 HuggingFace 下下来的原始 GGUF 文件（1.4GB）。**它只是原料**，Ollama 不会直接用它跑。
2. **`ollama create minicpm5-2b -f Modelfile.minicpm5`** 会把这个 GGUF 复制进 `blobs/`，并在 `manifests/` 写一条清单。之后 gguf 源文件就可以删了。
3. **真正在跑的是 `blobs/` 里的那份**（1.6GB，比源文件大是因为打包了模板和参数）。

### 5.3 常见操作

```bash
# 看有哪些模型、各占多大
ollama list

# 看模型规格（参数量、量化、上下文）
ollama show minicpm-v

# 看当前哪些模型驻留在内存里（keep_alive 生效的证据）
ollama ps

# 清理（释放磁盘；这两个命令会真删，确认后再执行）
ollama rm minicpm5-2b                          # 释放 1.6 GB
rm ~/.ollama/gguf/MiniCPM5-2B-Q4_K_M.gguf      # 释放 1.4 GB（导入后已可删）
```

### 5.4 一个要注意的坑

项目里的 `Modelfile.minicpm5` 现在写的是 `FROM ./models/MiniCPM5-2B-Q4_K_M.gguf`（相对路径，保证别人 clone 下来也能用）。但你当时下载的文件在 `~/.ollama/gguf/`。

**所以如果你要重新导入 2B 模型**，二选一：

```bash
# 方案 A：把 gguf 挪进项目（推荐，符合 Modelfile）
mkdir -p models && mv ~/.ollama/gguf/MiniCPM5-2B-Q4_K_M.gguf models/
ollama create minicpm5-2b -f Modelfile.minicpm5

# 方案 B：改 Modelfile 第一行为绝对路径（自己用可以，别提交）
```

`models/` 已在 `.gitignore` 里，不会被误提交（1.4GB 进 Git 会让仓库炸掉）。

## 六、想改东西时该动哪个文件

| 我想…… | 改哪里 |
|---|---|
| 换一个大模型试试效果 | `config.py` 的 `LLM_MODEL`（或用 `LLM_MODEL=xxx` 环境变量） |
| 加一份新制度文件 | 放进 `data/docs/制度文件/`，然后 `python -m app.ingest` |
| 加一个新场景（比如"财务报表说明"） | `data/docs/` 下建子目录，`config.py` 的 `SCENARIOS` 加名字 |
| 让系统更保守（更多拒答） | 调高 `CONF_HIGH`/`CONF_LOW`，跑 benchmark 看拒答正确率和漏答率 |
| 改回答风格/话术 | `rag.py` 的 `SYSTEM_PROMPT`（改完跑 benchmark 验证没跑偏） |
| 加测试用例 | `app/qa_set.json` 追加一条（`id/type/question/keywords/should_refuse`） |
| 改界面布局 | `ui.py`（三块：侧边栏 / render_answer / 主区对话循环） |
| 加一个 API 端点 | `main.py` |

改完任何一项，**验收动作固定是这三条**：

```bash
python -m app.ingest              # 改了文档/切分才需要
python -m app.benchmark --no-llm  # 秒级，先确认检索层没退化
python -m app.benchmark           # 完整跑，看 24 条明细
```
