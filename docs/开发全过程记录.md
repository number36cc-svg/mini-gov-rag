# 开发全过程记录：每一步是怎么想出来的

> 这份文档记录的不是"做了什么"，而是**为什么这么做、当时还有哪些选项、为什么否掉它们**。
> 代码谁都能写，判断力写不出来——这份文档就是判断力的原始记录。
>
> 配套：[技术原理详解.md](技术原理详解.md) 讲技术原理，[项目结构与文件说明.md](项目结构与文件说明.md) 讲代码地图。

## 一、起点：为什么要做这个项目

起点不是"我想学 RAG"，而是一个具体的求职目标：面壁智能「产品解决方案专家（政企 AI）」这类岗位。

这类岗位的招聘悖论是：**它要求你有政企 AI 落地经验，但经验要靠项目攒；而你没有公开项目，就进不去能攒经验的位置。**

所以目标定得很具体：**不是"学会 RAG"，而是"做出一个能让面试官在 5 分钟内判断我懂政企落地"的东西。**

这个目标一确定，后面所有决策都有了判据：**每个设计都要能回答"这东西让面试官多信我一分吗？"**

---

## 二、需求不是想出来的，是"复盘"出来的

### 2.1 第一版想法被自己否掉了

最初的设计是标准 RAG demo：文档切分 → 向量检索 → 大模型回答 → 带引用。

然后自己否掉了。理由很直接：**GitHub 上这种项目有几万个**，面试官看一眼就知道是教程复刻。它能证明"会调库"，证明不了"懂业务"。

### 2.2 转折点：翻出交付复盘

真正的转折是翻出自己过去做的多省交付复盘（已脱敏）。那些记录里全是"系统不好用"的具体表现，而每一条都能翻译成一个技术需求：

| 复盘里的原话（脱敏） | 背后的真问题 | 翻译成技术设计 |
|---|---|---|
| "财务数据保密要求高，不支持远程提供完整业务数据" | 云端 API 方案在这类客户**根本不可行**，不是"贵一点" | 端侧/私有化是唯一解 → 全本地栈 |
| "现场实施成本高、多项目并行人力紧张" | 客户的日常操作问题长期靠人肉响应 | 操作辅助场景：报错解读、操作指引自助化 |
| "不同机构记账规则、操作配置差异明显，标准模板无法通用" | 差异化知识散落在各项目组，没有沉淀 | 多机构知识组织 + 按机构检索 |
| "政策文件多版本并存，以最新版为准，修订后业务同步容易滞后" | 检索到旧版本 = 答错，而且是**最难发现的错** | 版本时效管理：入库带版本号，检索优先最新生效版 |
| "系统提示模糊，客户看不懂"（多个省的共性问题） | 模型答不出来时要能说"不知道"，不能编 | 三道闸可追责拒答 |

**这一步是整个项目的分水岭**：需求从"我猜客户要什么"变成"复盘记录告诉我客户卡在哪"。前者是想象，后者是证据。

### 2.3 于是"差异化"不是包装出来的，是长出来的

普通 RAG demo 缺的恰好是这四件事：

- 版本时效管理（市面 demo 基本没有，因为 demo 语料只有一个版本）
- 可追责拒答（demo 追求"答得出来"，政企追求"答不出来就说答不出来"）
- 多机构差异化知识（demo 语料是通用百科，没有"同一份制度两个机构有差异"这种结构）
- 一键 POC 报告（这是**售前岗位特有的**诉求：验收要有据可依）

这四项写进 README 的时候不是"特性列表"，而是"痛点→解法"的映射表。面试官能顺着这条线追问到任何一层。

## 三、六个技术岔路口

每个岔路口都记下：**当时的选择是什么、判据是什么、事后验证如何**。

### 岔路 1：端侧 vs 云端 API

- **选项**：调 OpenAI/通义/文心的 API（效果好、两天能做完）／ 本地跑开源模型（效果差一档、环境麻烦）
- **判据**：客户是财政/政务单位，**数据出域是合规否决项，不是成本项**。云端方案在这些客户里连投标资格都没有
- **选择**：全本地。并且把这个约束写进 `.cursor/rules/project.mdc` 的硬约束第一条（"禁止调用任何云端 LLM API"），防止 AI 顺手给我接个云端接口
- **事后验证**：整个项目零云端调用，POC 报告里可以写"数据不出域"这条硬声明——**这条声明在政企投标里值钱**

> 这个判断的关键不是技术，是**知道合规是硬门槛而不是偏好**。这是做过政企项目的人和只做过 to C 的人最大的差别。

### 岔路 2：为什么是 MiniCPM

- **选项**：Qwen2.5-7B（中文强、生态好）／ Llama 系／ MiniCPM 系（面壁自家）
- **判据**：三条，按权重排——
  1. **端侧定位要成立**：客户是普通办公本，不是 GPU 服务器。参数量直接决定"能不能在 16GB 机器上同时开浏览器办公软件运行"
  2. **求职目标对齐**：面壁的岗位，用它自家的模型是"做过功课"的信号，也是能聊起来的话题
  3. **中文制度文本理解够用**：制度问答是"检索到位 + 照抄条款"，不需要模型自己推理——这是本项目最重要的一条技术判断
- **选择**：MiniCPM 系，实测两个规格：
  - `minicpm-v`（7.6B + 视觉投影，5.5GB）→ **主测模型**
  - `minicpm5-2b`（2.5B，1.6GB）→ 低配备选
- **事后验证**：两个都跑过 24 条用例，7.6B 的条款复述完整度明显更好，2B 在多步版本对比题上不稳定。**结论写进 README 而不是藏起来**——"2.5B 在 M1 上跑到 X 秒但多步推理不稳定"比"用了大模型效果很好"更能说明端侧方案的可行性边界

### 岔路 3：向量数据库 vs numpy 暴力检索

- **选项**：Chroma / Milvus / FAISS（"正规"做法）／ numpy 一次矩阵乘
- **判据**：切片量。287 条 × 512 维矩阵乘是**微秒级**，加一个向量库服务带来的是：多一个进程、多一份运维、多一个客户现场装不上的风险
- **选择**：numpy（初版其实用了 Chroma，后来拆了）
- **事后验证**：检索层实测 22-245ms（含 embedding 编码），瓶颈完全不在暴力检索上
- **但这条判断有边界**：上到十万级切片就该换。README 和技术文档都写明了"什么时候该换"，因为**知道工具的上限比会用工具更重要**

### 岔路 4：按条款切 vs 固定长度切

- **选项**：`RecursiveCharacterTextSplitter(chunk_size=500)`（教程标配）／ 按"第X条"边界切
- **判据**：用户问的问题就是"第几条怎么规定"，**检索单元应该是用户认知里的单元**。500 字固定切会把第三十九条和第四十条合并成一片，检索到了也说不清是哪一条
- **选择**：按行首条款编号切，一条一片（平均 122 字）
- **事后验证**：切分粒度从 500 调到 300 后基本做到一条一片；这个改动直接决定了后面"版本比对"能不能做（按条款对齐才可能 diff）

### 岔路 5：让模型做版本比对 vs 用代码做

- **选项**：把两个版本的条款都塞给模型，让它找差异（自然语言做法）／ 用代码按条号对齐后做文本 diff，把结论作为"已知事实"喂给模型
- **判据**：版本比对是**确定性任务**（字符级比对），交给概率模型做是浪费且不可靠
- **选择**：`version_article_diff()` 程序化比对，模型只负责"把结论说成人话"
- **事后验证**：这是本项目最有工程味道的一处设计——**能确定性计算的事不要交给模型**。V04 那条题模型表述不完整，但程序给出的比对结论是对的

### 岔路 6：先做微调 vs 先做检索层

- **选项**：用 LoRA 在制度问答对上微调（看起来"高级"）／ 先把切分、检索、拒答做扎实
- **判据**：ROI。制度问答 80% 的失败来自"没检索到正确条款"，不来自"模型不会说"。检索层每提升 1%，效果提升远大于微调
- **选择**：先检索层。微调列为路线图待办（README 里有）
- **事后验证**：未通过的 3 条全是"检索到了但模型多步推理不稳"——这恰恰说明**瓶颈已经移到生成层了**，下一步才是微调或换更大模型。这个判断有数据支撑，不是空话

## 四、九个坑（这部分是面试最容易被追问的）

按发现顺序，每个都记：**现象 → 排查 → 根因 → 修法 → 教训**。

### 坑 1：条款编号错位

- **现象**：检索"预备费"命中的切片里同时出现第三十九条和第四十条的内容，引用定位不准
- **排查**：打印切片原文，发现切分点落在一句"……依照本法第四十条规定……"的中间
- **根因**：用正则 `第[一二三四五六七八九十百]+条` 匹配所有出现位置，把**正文里的引述**当成了条款起点
- **修法**：只认**行首**的条款编号（`ARTICLE_BOL_RE`，锚定 `^`）
- **教训**：切分规则要匹配"文档结构"，而不是"文本里出现的模式"。结构信息（行首/缩进/编号层级）比模式匹配可靠

### 坑 2：Markdown 表格被合并成 415 字大块

- **现象**：报错对照表（一行一条报错）检索时，问某一条报错，命中的切片里塞了二十条报错
- **根因**：表格按段落切分，整个表格是一个段落
- **修法**：识别表格类文档（含 `｜` 竖线），**按行切分 + 每行补表头**
- **教训**："文档形态分流"是必要的。一套切分策略打不了所有文档——法规看条款，手册看表格行

### 坑 3：切片膨胀到 6458 字（最阴的一个）

- **现象**：某几个切片长度异常（正常 122 字，这几个 6000+ 字），检索质量被严重稀释
- **根因**：滑窗重叠代码写了 `buf[-CHUNK_OVERLAP:]`，而 `CHUNK_OVERLAP = 0` 时 `buf[-0:]` **等于整个字符串**（Python 切片的负零陷阱）——于是每次循环都把整个 buf 拼上去，滚雪球
- **修法**：判 `CHUNK_OVERLAP > 0` 才做重叠
- **教训**：`x[-0:]` 不是空串，是全部。这类"语言特性造成的静默错误"只能靠**加断言/看数据的分布**发现——所以建库后一定要打印切片长度分布，不能只看"成功切了 287 片"

### 坑 4：融合分被用来判置信度

- **现象**：问"我们单位去年非税收入多少"（应该拒答），被判成"依据充分"
- **排查**：打印分数发现融合分 0.570 很高，但纯语义余弦只有 0.431
- **根因**：混合检索分 = 0.6×余弦 + 0.4×字面重合。这句话含大量领域词（非税收入、单位、去年），字面重合把分数抬起来了
- **修法**：**排序用融合分，判档用纯语义分**——两个分数职责分开
- **教训**：一个指标不能同时服务两个目标。"排序"关心相对好坏，"能不能答"关心绝对可靠，混用就出错

### 坑 5：语料本身是错的

- **现象**：问"预算法自什么时间起施行"，答"1995年1月1日"
- **排查**：对照官方原文，2018 修正版应为"2015年1月1日"
- **根因**：从网页复制清洗时，某段落错了
- **修法**：修正语料，并加一条测试用例（N09）把这个事实钉死
- **教训**：**RAG 系统会忠实复述语料里的错误**。语料质量是检索系统的一部分，不是"外部输入"。这条在政企场景尤其致命——客户会拿你的答案去对外发文

### 坑 6：文件头污染检索

- **现象**：问"预算法第几条"时，命中的是文件开头的"中华人民共和国预算法（2018修正）"标题块，而不是具体条款
- **根因**：文件头包含法规全名，语义上与"预算法"高度相似，余弦虚高，把真条款挤出 top-3
- **修法**：丢弃文件头块（它不包含可回答的内容）
- **教训**：**看起来最"相关"的文本往往最没用**。检索系统的目标是"找到能回答问题的证据"，不是"找到最像问题的文本"

### 坑 7：小模型误拒（3 次里错 2 次）

- **现象**：明明检索到正确条款，模型却说"资料中没有相关内容"
- **排查**：换提示词试验，发现提示词里给了"如果资料不足请回答无法回答"这个出口，小模型**过度使用**这个出口——它学会了"拒答是安全选项"
- **修法**：三件事
  1. 收紧拒答条件：把"可以拒答"的表述改成"只有资料完全不含相关内容时才拒答"
  2. few-shot：给一个"资料里有答案就正常回答"的示例
  3. **二次确认机制**：检测到拒答后，换一个**没有拒答出口**的提示词（`EXTRACT_PROMPT`）重问一次；能抽出内容 = 第一遍是误拒（置信度降一档，诚实反映模型没把握）；抽不出 = 真拒答
- **教训**：给模型留逃生通道，它一定会用。**拒答的正确率靠机制保证，不靠 prompt 里的祈使句**

### 坑 8：版本去重键选错

- **现象**：同一个问题的 top-3 全被同一部法规的不同版本占满，其他相关条款挤不进来
- **根因**：去重键用了 `chunk_id`（每条切片唯一，等于没去重）
- **修法**：去重键改成 `(source, page, 条序号)`，同一位置只留最新生效版本
- **教训**：去重的本质是"定义什么算同一个东西"。键选错，去重等于装饰

### 坑 9：`--no-llm` 覆盖了正式报告

- **现象**：跑完完整测试（21/24），又跑了一次快速自检，`reports/POC测试报告.md` 变成了 20/24
- **根因**：两种模式的输出路径都是同一个默认值
- **修法**：按模式分文件（`POC测试报告.md` / `POC测试报告_检索层.md`）
- **教训**：**看起来无害的默认值最容易埋雷**。任何"写文件"的工具都该想一下：多跑一次会发生什么

## 五、性能问题：从"卡很久"到 6 秒

这是全项目最能体现"排查思路"的一段。

### 5.1 现象

演示时点第一个问题，等了很久（体感接近一分钟）才出结果，但 `benchmark` 里平均只有 9.6 秒。

### 5.2 排查路径（关键：不要猜，要分离变量）

1. **先怀疑检索**：打印检索耗时 → 22-245ms，**排除**
2. **再怀疑 embedding 加载**：发现每次提问都会调 `get_model()`，但它是全局单例，Streamlit rerun 不会重新 import 模块 → 只在首次加载。**不是主因**
3. **对比两次调用**：手动连续调两次 Ollama，第一次 43 秒，第二次 6 秒 → **强烈怀疑冷热态差异**
4. **查证冷热态**：`curl localhost:11434/api/ps` → 提问前模型不在内存里
5. **定位到 Ollama 的行为**：默认 `keep_alive=5m`，闲置 5 分钟就卸载模型。benchmark 跑完隔了一个多小时，模型早就被卸载了，第一问要把 5.5GB 从磁盘读进内存

### 5.3 修复（三处，缺一不可）

| 改动 | 解决什么 |
|---|---|
| 请求带 `keep_alive=60m` | 模型常驻内存，不再反复冷启动 |
| 页面打开即**后台线程**预热 embedding + LLM | 用户点第一个问题时模型通常已热，页面本身秒开 |
| `get_model()` 加**双重检查锁** | 预热线程与用户提问并发时不会重复装载模型 |

### 5.4 顺带修掉的一个体验问题

UI 的等待提示写的是"检索制度条款中…"，但检索只要毫秒级，**99% 时间花在模型加载和生成上**。提示误导了等待感受。

改成 `st.status` 分阶段：先"检索制度条款…"，再"本地模型生成回答中…（首次或闲置后需加载模型，约 30-60 秒；常驻后 10 秒内）"。

### 5.5 结果与教训

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 冷启动第一问 | 43 秒（体感更久，因为无进度提示） | 页面打开即预热，用户基本感知不到 |
| 热问答 | 6-10 秒 | 6-10 秒（不变，这已是 7.6B CPU 推理的真实水平） |

**教训**：
- **benchmark 数据和端到端体验之间的差距，往往就是冷/热态差距**。只看平均值会漏掉"第一次体验"
- 等待时间要"花在哪说清楚"。同样等 40 秒，有进度提示和没有是两种体验
- 演示类系统必须做**预热**——演示的第一分钟决定别人对你整个项目的判断

## 六、我是怎么用 AI 做这个项目的

这部分可能比代码更有参考价值，因为它记录了一次**失败的协作方式和迭代后的方式**。

### 6.1 第一版协作方式：我当"路由器"（失败）

流程是：跟 AI 讨论 → AI 输出方案 → 我复制给 Cursor → Cursor 改代码 → 我把报错贴回来 → 循环。

**问题**：
- 我成了信息中转站，每次交接都在丢上下文
- 一个报错要来回三四轮，每轮我都要复制粘贴
- 我的注意力全花在"搬运"上，而不是"判断"上

### 6.2 第二版：把规则写进项目，让 AI 自己验收

在 `.cursor/rules/project.mdc` 里加了两块：

**自检协议**——AI 干完活必须自己走完：跑起来、看报错、自己修（最多 2 轮）、只汇报三行（改了什么 / 命令+原始输出 / 通过与否）。**不允许把半成品交给人。**

**额度纪律**——不重构、不"顺手优化"、不生成用不到的示例、一次只做当前那一步。这条直接来自一个真实教训：AI 越界把整个项目做完了，导致"这个项目到底是谁做的"都说不清，也很难在面试里讲自己的思考过程。

### 6.3 我的判断：AI native ≠ AI 数量多

中间认真考虑过"多个 AI 并行"的工作流（一个写代码、一个 review、一个写文档）。

结论是**否掉**，理由：这个项目的九个步骤是**强串行**的（切分错了，检索就没意义；检索错了，拒答阈值就调不准），没有并行度。多 Agent 在这个项目里只会增加编排成本，不会缩短关键路径。

真正的 AI native 是两件事：
1. **交接次数少**（把规则写进项目，让 AI 自己闭环）
2. **判断落在正确的环节**（人负责"做什么、为什么"，AI 负责"怎么做"）

### 6.4 分工实录

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 需求从哪来、要证明什么 | 我 | AI 不知道我的交付复盘里有什么 |
| 痛点 → 设计映射 | 我定方向，AI 补充 | 判断需要业务经验，补充需要检索能力 |
| 技术选型 | 我拍板，AI 列选项和代价 | 选型是判断题，不是知识题 |
| 写代码 | AI 为主 | 主要是样板量大 |
| 踩坑排查 | 我提供现象，AI 提假设，**我验证** | AI 猜得很快，但猜错也很快，必须用真实输出验证 |
| 技术文档 | AI 起草，我审校 | 细节多、结构要求高；但"为什么"必须我自己认账 |
| 演示脚本、命名、文案 | AI | 体力活 |

还有一个具体的成本考虑：**额度是有价的**。所以策略是——Markdown 文档、语料清洗、排错这类"不需要 Cursor 上下文"的活，在对话里做；Cursor 只用来改代码。这样额度花在最需要"看得到整个仓库"的地方。

## 七、如果重做，我会改什么

诚实记录，不美化：

1. **一开始就加断言**：切片长度分布、向量模长（必须全为 1.0）、去重后条数。坑 3（6458 字切片）如果有断言，10 秒就能发现，而不是等到检索质量异常才回头查
2. **语料先做校验**：坑 5 是语料错误，应该在入库阶段做一次关键事实的自检（比如"施行日期"这类字段和官方源比对）
3. **性能预算前置**：项目开始就定"单问 10 秒内"，而不是做完再优化。冷热态问题如果有性能预算，第一天就会暴露
4. **测试集边写边攒**：现在是最后集中写 24 条。更好的做法是每发现一个 bad case 就加一条，测试集会自然长成"真实问题的集合"
5. **拒答阈值应该在更多语料上标定**：现在只有 6 份文档、24 条用例。真实客户的语料规模大两个数量级，阈值几乎肯定要重标——这个边界应该写进 README 的"已知限制"

## 八、面试时怎么讲这个项目

### 8.1 三分钟版（结构：为什么→做了什么→结果→判断）

> "我在政企非税/缴费方向做售前，过去几年攒了一堆交付复盘：客户财务数据保密不能出域、现场实施人力不够、不同机构规则差异、政策多版本并存。
>
> 我把这些复盘翻译成了一个端侧 RAG 系统：普通笔记本跑 MiniCPM，数据不出内网。核心不是把 RAG 跑起来，而是针对政企场景做了四件事——版本时效管理（检索优先最新生效版，能新旧条款比对）、三道闸可追责拒答（答不出来就说答不出来）、多机构差异化知识、一键 POC 报告。
>
> 实测 24 条用例通过 21 条，拒答正确率 100%，热问答 6 秒，全部在本机 M1 16GB 上跑的。
>
> 最重要的判断是：**小模型做垂直场景，可靠性必须建立在检索层和闸门上，不能指望模型自己推理**。所以力气全花在切分、混合检索、拒答机制上，微调排在后面。"

### 8.2 大概率会被追问的 5 个问题

| 追问 | 怎么答（要点） |
|---|---|
| 为什么不用向量数据库？ | 287 条切片，numpy 矩阵乘微秒级。上十万级再换。**知道边界比会用工具重要** |
| 拒答准确率怎么保证的？ | 三道闸 + 二次确认。核心是"不能只靠阈值"，因为"不存在的第 200 条"相似度比真问题还高 |
| 2B 小模型效果够吗？ | 不够，所以主测用 7.6B。2B 在多步版本对比上不稳定——**这是端侧方案的可行性边界，我把它写进 README 而不是藏起来** |
| 这跟市面 RAG 产品差在哪？ | 版本时效管理和多机构差异是制度类知识库的特有结构问题；POC 报告是售前动作的产品化。市面 demo 语料只有单一版本，遇不到这些问题 |
| 你在这个项目里最得意的设计？ | 版本比对用代码做、只让模型"说人话"。确定性的事不要交给概率模型 |

### 8.3 一个加分点：主动说边界

主动交代"哪些没做好、为什么、下一步怎么做"，比把 24 条说成"全部通过"可信得多。

这个项目里可以主动说的三条：
- 3 条版本对比题未通过，根因是模型多步推理不稳 → 下一步是 rerank + 程序化 diff 兜底
- 拒答阈值只在小语料上标定过 → 真实客户语料要重标
- 只做了单机单模型，没做并发压测 → 生产环境要补推理引擎选型和硬件容量规划

**能说清边界的人，才被认为真的做过。**
