## 1. 全景：一条问答请求的生命周期

```
用户提问「预备费按什么比例设置？」
        │
        ▼
┌─ ① 检索路由（rag.retrieve）
│     判断：是普通问题，还是版本对比问题？
│      ├─ 普通问题 → 混合检索 → 版本去重（只留最新生效版）
│      └─ 对比问题 → 结构化定位（按条款号直接捞）或每版本各取几条
        │
        ▼
┌─ ② 混合检索（rag.search）
│     语义余弦（bge 向量点积）× 0.6 + 字面重合度 × 0.4 → 排序取 top 候选
        │
        ▼
┌─ ③ 三道闸（rag.answer）—— 决定"答不答"
│      闸一：纯语义相似度 < 0.52 → 拒答
│      闸二：问题点名了「第X条」但库里没有这条 → 拒答
│      闸三：模型读完资料后自述答不了 → 改判拒答
        │
        ▼
┌─ ④ 生成（rag.ask_llm → Ollama 本地 MiniCPM）
│     只依据检索条款回答，每句带出处，温度 0.3
        │
        ▼
   返回 {回答, 置信度档位, 引用列表[文件名+版本+页码], 相似度}
```

对应代码位置：`app/main.py`（API 入口）→ `app/rag.py`（①②③④）→ `app/ingest.py`（离线建库）→ `app/benchmark.py`（验收）。

离线入库链路（`python -m app.ingest`）：

```
data/docs/ 下文档 → 解析（md/pdf/docx） → 切分（三套策略按文档形态分流）
→ bge 向量化（L2 归一化） → vectors.npy + chunks.json + meta.json
```

## 2. 需求从哪来：四个真实痛点 → 四个核心设计

这个项目的需求不是"学 RAG 顺便做个 demo"，而是从多省政企客户实施交付复盘里提炼出来的（已脱敏）。每条痛点直接对应一个模块：

| 交付现场的真实问题 | 对应设计 | 代码位置 |
|---|---|---|
| 保密数据连远程提供都不允许 → 云端 API 方案在这种客户那里根本不可能 | **全本地运行**：模型、向量、索引全部在本机 | `config.py` 的 OLLAMA_URL 是 localhost |
| 政策文件多版本并存，客户问规定必须"以最新版为准" | **版本时效管理**：普通问答自动只留最新版；明确问"改了什么"才对比 | `rag.keep_latest_versions` / `retrieve` |
| 客户最怕 AI 编造——答错了要担责，宁可自己查原文 | **三道闸拒答**：宁可少答，不可错答 | `rag.answer` 的闸一/二/三 |
| 系统报错提示模糊，用户看不懂，长期依赖实施人员驻场 | **操作辅助场景**：报错对照表入库，按机构区分规则 | `data/docs/运维手册/`、scenario 元数据 |

这个映射关系本身就是方案设计方法论：**需求不来自技术清单，来自交付现场的失败记录。**

## 3. 文档解析与切分：检索单元决定检索上限

### 3.1 核心原理：切分是 RAG 效果的第一瓶颈

向量检索的本质是"问题向量和切片向量比相似度"。切片切得好不好，决定了：

- **语义纯度**：一个切片混进 N 个不相关主题，每个主题的语义都被稀释，相似度全体下降
- **引用精度**：检索到了，但说不出是哪一条，溯源就失效了

所以本项目的切分原则是：**检索单元 = 语义完整单元**，而不是教程里通用的"每 500 字切一刀"。

### 3.2 三套策略按文档形态分流

```
表格型文档（报错对照表）→ 每行一个切片，并把表头拼进每行当字段说明
条款型文档（法规）      → 按「第X条」切，一条一片，不合并
说明型文档（操作手册）  → 按段落合并到 300 字，保住操作步骤连贯性
```

每套策略都有实测依据：

**法规为什么一条一切片？** 最初按 500 字合并时，实测《预算法》第三十九、四十、四十一条经常被合进同一切片——检索到"预备费"（第三十九条），但引用说不清是第几条，客户追问一条就露馅。法规条款平均 150 字，天然是完整规范单元。调成一条一片后，平均切片 123 字，引用可以精确定位到条。

**表格为什么按行切？** 最初把报错对照表当普通文本处理，8 条报错被压成两三个 415 字的大切片，每片混着七八条不相干的报错——"账号已锁定"的检索结果里混着"导出超上限"，全部不准。按行切之后一行报错一片，直接命中。补表头的原因：表格行的单元格只有值没有字段名（"已实时推送须先红冲"——什么的已推送？），把表头拼上语义才完整。

### 3.3 两个真实踩过的坑（比策略本身更有讲解价值）

**坑一：正文引述导致条款编号整体错位。**
法规正文里会出现「依照本法第四十条规定报送备案的预算」这类**引述**。第一版切分用全文正则匹配「第X条」，把引述也当成了新条款的起点——2014 版《预算法》从这条引述开始，后面所有条款编号**整体错位一条**，"第三十九条"的切片里装的是第四十条的内容。这是最隐蔽的 bug：索引能建、检索能跑、看起来一切都对，只有逐条对比原文才能发现。

**修法**：只认**行首**的条款标题（`(?m)^\s*第X条`）。条款编号在法规排版里永远是新起一行，正文引述永远在句中——这一个约束就消除了全部误判。教训：**用结构特征（排版位置）而不是内容特征（关键词）做切分边界**。

**坑二：文件头污染检索。**
法规文件开头有「中华人民共和国预算法（2014年修正）…2014年08月31日 全国人大常委会」这样的元信息。它不含任何规范内容，却塞满了"预算法""修正""人大常委会"这类**制度领域词**——问"预算法自什么时间起施行"，文件头的余弦分比真正的答案条款（第一百零一条）还高，top1 永远是文件头。修法：第一条之前的内容直接丢弃。教训：**元数据级别的文本对检索是负资产**，宁可丢也不能入库。

**坑三（送一个 Python 语言的）：`buf[-0:]` 等于整个 `buf`。**
切片合并时用 `buf[-CHUNK_OVERLAP:]` 取重叠，当 `CHUNK_OVERLAP=0` 时 `-0 == 0`，取的是**从头到尾的整个 buf**——每个切片把上一块全文吞进来，切片越滚越大，实测平均切片一度膨胀到 6458 字。修法：显式判断 `CHUNK_OVERLAP > 0`。教训：负索引从尾部取数的语义在 0 这个点上会反转，参数化代码必须对 0 值做显式分支。

### 3.4 为什么不用向量数据库（面试必问）

切片量千级时，numpy 一次矩阵乘法（`vectors @ qvec`）就是全库暴力检索，毫秒级出结果。引入 Milvus/Chroma 意味着：多一个服务要装、要启动、要配持久化——**运维成本大于检索收益**。上量到十万级、需要增量更新和元数据过滤时再换，接口不变只换实现。这个判断本身是工程取舍的展示：**技术选型跟着数据规模走，不跟着技术流行度走。**

## 4. 向量化：为什么是 bge-small-zh，为什么必须归一化

**模型选择**：BAAI/bge-small-zh-v1.5，约 95MB，CPU 上毫秒级编码。选它的原因：中文语料训练、体积小到笔记本无感、检索效果在中文公开评测里同体积最好。政企语料 99% 是中文，用英文模型（如 all-MiniLM）是明显错误。这里同理埋着一条产品逻辑：**端侧方案选模型，先看显存/内存预算，再看效果**——512 维 × 千级切片，索引总共不到 1MB。

**L2 归一化**：编码时 `normalize_embeddings=True`，把每条向量归一化到单位长度。这样两个向量点积就**等于**余弦相似度，检索循环里少一步范数计算；更重要的是相似度被约束到 [-1, 1]，后面的置信度阈值才有稳定的语义。

**query 加指令前缀**：bge 系列做检索时，query 侧要加固定前缀「为这个句子生成表示以用于检索相关文章：」——这是模型训练时的用法约定，漏掉会损失召回（**passage 侧不加**，两侧对称加反而错）。这类模型使用细节只有读过 model card 才知道，是面试里区分"跑过"和"跑明白"的点。

## 5. 混合检索：纯向量检索输在哪

### 5.1 实测暴露的问题

纯语义检索在一类问题上不稳：**用户原词直问**。比如运维场景问"登录提示账号已锁定，需要等多久"——知识库原文就写着"账号已锁定，30 分钟后解锁"，但 bge-small 只有 512 维、对短查询的语义压缩有损，相似度反而不如字面匹配稳。

### 5.2 解法：语义 + 字面加权

```
排序分 = 0.6 × 语义余弦 + 0.4 × 字面重合度
字面重合度 = query 的二元字组（bigram）在切片文本中的覆盖率
```

二元字组就是"账号已锁定"→ {账号, 号已, 已锁, 锁定}，中文分词的最简替代——不需要分词器，天然鲁棒。权重 0.4 是在本项目语料上试出来的平衡点：字面占比太高会退化成关键词匹配（同义改写的召回丢失），太低救不了原词直问。

### 5.3 一个反向教训：排序分不能用来判置信度

这是本项目最值得讲的取舍：混合排序分提升了**排序**质量，但**判档**（答不答）必须用纯语义余弦。因为字面重合度会让"含领域词但答不了"的问题虚高——「我们单位去年的非税收入是多少」字面上全是制度词，排序分 0.6+，但语义上知识库根本没有这类数据。用排序分判档必然误判。**排序和判档是两个目标，混用同一个分数是隐性 bug**——这个错误我自己先犯了一遍，测试抓出来的。

## 6. 版本时效管理：政企场景的刚需，市面 demo 的空白

### 6.1 问题定义

同一份法规存在多个修正版本（本项目用《预算法》2014 修正 + 2018 修正演示）。两类问题要分开处理：

- **"预备费按什么比例设置？"** → 答案应该是**现行有效版**的规定。把两版并排贴出来让用户自己判断哪版有效，等于把判断责任推回给客户——政企场景里这等于没做版本管理。
- **"2018 修正相比 2014 改了什么？"** → 明确要求对比，此时才把多版本都捞出来。

### 6.2 实现：三个机制

1. **版本元数据**：文件名约定 `文件名_版本标识.md`，入库时正则解析出 `source` 和 `version`。用文件名而不是文档内容做版本识别，是因为公文排版不统一，正文里未必有干净的版本标识。
2. **普通问答的版本去重**（`keep_latest_versions`）：多取 3 倍候选 → 同一份文件的**同一条文**只保留版本号最新的 → 取 top_k。版本排序键：`2018修正 → 2018`，`现行 → 9999`。
   去重键必须用**条款号**而不是切片序号——两版条款编号存在偏移时序号对不上，去重直接失效。实测症状：问预备费比例，引用里同时出现 2014 与 2018 两版，"以最新版为准"的承诺当场破功。条款号是跨版本唯一稳定的锚点（`第四十条` 在两版里都是同一条）。
3. **对比问题的结构化检索**：问题含"修订/变化/区别"等词时走对比路由。这里有个妙点——如果问题点名了「第X条」（比如"两版第五十一条引用的条款号一样吗"），**直接按条款号把每个版本的这一条捞出来**，不走向量检索。因为"两版第X条引用的条款号一样吗"这种**元问题**，语义向量根本表达不出检索意图，而条款号是精确线索。**结构化信息存在时，优先用精确匹配而非语义匹配。**
4. **程序负责判定，模型负责表述**（`version_article_diff`）：把各版本同一条文的文本取出来、去空白后逐字比较，得出"完全一致 / 存在实质差异"，并把原文差异作为【程序核对结果】注入提示词，要求模型必须采用该结论、只做表述。

   为什么必须这么做：两版《预算法》第五十一条只差一个条号引用——2014 版是「依照本法**第四十条**规定报送备案」，2018 版是「依照本法**第五十条**规定报送备案」。这不是语义层面的差异，向量检索和语言模型都不可靠：实测模型给出了自相矛盾的答案——"不一样，2014 引用第五十一条，2018 引用第五十一条"。

   **这条通用的工程原则值得记住：凡是能确定性判定的，就不要交给模型。** 字符级 diff、数字比对、日期先后，代码做是 100% 准确；模型做是概率。模型该负责的只有"把结论说人话"。这一条也回答了"为什么不把整个版本对比都交给 Agent"。

### 6.3 为什么这套东西值钱

通用 RAG 教程不涉及版本问题，但它恰是政企客户验收时必问的场景（政策文件每周都在更新，"以最新版为准"是刚需）。这一节在面试里可以自然引出 RAG 与微调的经典取舍：**制度知识放 RAG 不放进模型，就是因为知识每周更新、且必须可溯源到具体版本**——微调出来的知识两者都做不到。

## 7. 三道闸拒答：宁可少答，不可错答

### 7.1 为什么一个阈值不够

课程 demo 的拒答 = 相似度 < 阈值就拒答。实测在本项目语料上这必然出事，原因是**相似度分数会被"字面像制度"的问题骗过**：

- 「预算法第 200 条规定了什么」——法规只有 101 条，这问题在考你"编不编"。但它的向量相似度 **0.6+，比很多真问题都高**，因为整句话全是制度领域词。
- 「个人所得税专项附加扣除标准」——语料里完全没有，但和财税语料的余弦分落在正例区间。

同时阈值本身有重叠区：正例 top1 相似度实测 0.49~0.84，负例 0.43~0.59——**任何单一阈值都同时存在误答和误拒**。所以设计成三道串联的闸，每道闸用不同的信息源：

| 闸 | 信息源 | 拦什么 | 代码 |
|---|---|---|---|
| 闸一：语义阈值 | embedding 余弦 | 明显无关的问题 | `grade_confidence` |
| 闸二：条款号校验 | 结构化匹配 | 点名了不存在的条款（编造考题） | `article_ref_missing` |
| 闸三：模型自述 | LLM 对资料的可答性判断 | 资料相关但确实答不了 | `llm_says_cannot_answer` + `EXTRACT_PROMPT` 二次确认 |

### 7.2 每道闸的实现细节

**闸一**用纯语义余弦（见 5.3 的教训），阈值 0.62 / 0.52 分"依据充分 / 部分依据 / 无法回答"三档，对应界面绿黄红标签。注意阈值只做"明显无关"的粗筛，精确判定交给后两道闸。

**闸二**是针对性防线：用户常写「第 200 条」（数字间有空格），所以先去掉全部空白再匹配条款号；切片侧同样做空白归一后检查该条款是否真的被检索到。没有就明确告知"知识库中没有这一条，可能条款号有误"——**把"答不了"的原因说清楚，本身就是政企客户要的体验**。

**闸三**的实现有个关键设计：prompt 里要求模型"答不了就只输出一句话：依据现有制度文件无法回答该问题"。于是代码侧判定就变得可靠——**回答很短（≤80字）且回答中含拒答词**就改判拒答并清空引用。这是代码判定，不靠模型自觉；如果允许模型长篇发挥，就没法用代码区分"真拒答"和"编了个开头说答不了然后开始编"。

**闸外的第四种情况：环境故障不能伪装成能力。** 模型服务没起、模型没下载、响应超时——这些情况返回带 `【模型不可用】` 前缀的提示和置信度"服务不可用"，绝不返回一个"依据充分"的空答案。这是从交付现场得到的教训：**演示时把环境故障当好结果，客户上线后发现，信任直接归零。**

### 7.3 拒答的输出设计

拒答不是甩一句"不知道"，而是带三条出路：换原文表述重问 / 咨询归口管理部门 / 请管理员补充文件。政企系统的拒答必须**可追责、有兜底**——这是从"AI 答错谁负责"这个真实客户问题倒推出来的设计。

## 8. 生成层：prompt 设计与参数

**System prompt 的五条规则**，每条对应一类失败模式：

| 规则 | 防什么失败 |
|---|---|
| 只依据参考资料，不用外部知识 | 模型幻觉（用了参数里过时的旧规定） |
| 每句标「（依据：《文件名》版本 第X页）」 | 不可溯源——政企场景一票否决项 |
| 答不了只输出固定一句话 | 模型硬编（同时服务闸三的代码判定） |
| 数字、比例、时限务必照抄原文 | 模型"改写"数字（0.5% 抄成 5% 的灾难） |
| 同一条款有版本差异时必须指出 | 版本管理失效的最后一道保险 |

**temperature=0.3**：制度问答要的是确定性不是创造性，低温抑制发挥；但不是 0——0 会让部分模型输出重复循环。**MAX_TOKENS=320**：一个条款的答案 200 字内说得清，上限压低能明显减少小模型的空话与耗时。

### 8.1 提示词实测迭代：拒答的"逃生通道"被模型抓走

这是本项目最典型的一次"指标难看但病因意外"的排查，值得完整记录。

**症状**：完整测试第一轮，9 条应答题被判"误拒答"——但检索层的语义分 0.60~0.80，正确条款明明已经在提示词里。等于**模型拿着正确答案说"我答不了"**。

**定位方法**：绕开三道闸，直接看模型原始输出（`rag.ask_llm` 的返回值）：

```
Q: 票据作废时提示「已实时推送，须先红冲」…      → "依据现有制度文件无法回答该问题。"
Q: 预算法关于预备费设置比例的规定，两版有区别吗？ → "依据现有制度文件无法回答该问题"
```

**对照实验**：同样的资料、极简提示词（"只依据资料回答，末尾注明资料序号"）——模型答得**完全正确**，还准确转述了红冲四步流程。

**根因**：原 system prompt 里有一条规则「如果参考资料不足以回答，只输出这一句话：依据现有制度文件无法回答该问题」。这条规则本意是配合闸三做代码判定，但对照料型文本（表格行、含「｜」分隔符）、对"版本对比"这类需要推理的提问，8B 级模型会**把这条逃生通道当成默认选项**——它不确定自己答得对，就按规则拒答。**指令越严格，小模型越倾向于走最安全的那条路。**

**修法四条**：
1. 拒答条件收紧为"资料与问题**完全无关**"（举例说明什么算无关），并补一句"只要资料里出现相关信息就回答，不得拒答"
2. 显式告诉模型「｜」是表格分隔符、按位置对应字段——不解释，模型会把表格读成乱码
3. 把"数字必须照抄"从"务必"升级为"必须照抄具体数值，不要概括成'一定数量'"
4. **加一条示例（few-shot）**：给一个"表格行 → 带数字带出处的回答"的完整样例。小模型对抽象规则的遵守度很差，但模仿示例很准——实测加示例后，原本漏掉"5000 条"的回答开始把数字写出来

**还剩下一个更麻烦的现象：拒答是随机的。** 同一问题连问 3 次，2 次拒答、1 次答对。这说明模型不是"不知道"，而是"不确定时走最安全的路"。继续把提示词写严只会让它更爱拒——于是加了**拒答二次确认**机制：

```
第一遍（正式提示词）→ 模型拒答
        ↓
第二遍（EXTRACT_PROMPT：不给任何拒答选项，只做抽取，找不到就输出"无"）
        ↓
   抽到了 → 判定为误拒，采用第二遍答案，置信度自动降一档（诚实反映模型没把握）
   抽不到 / 仍拒答 → 真拒答
```

这个设计的价值在于：**它把"拒答"从一次判断变成了两次独立判断的共识**，比调阈值和调提示词都稳。代价是拒答路径多一次推理（约 3 秒），但拒答本来就是少数路径。顺带它是 harness 思维的雏形——**当模型行为不稳定时，用流程约束代替参数调优**。

**修后**：N09「预算法自什么时间起施行」、V04「两版预备费比例有区别吗」、O04「日终处理失败是故障吗」全部从误拒答变为正确答案。

**这条经验的普适结论**：小模型的提示词里，**任何一个"可以不做"的分支都会被滥用**。给逃生通道必须附带严格的触发条件，否则它会变成主路。而且这类问题在"检索指标"上看不出来——检索全对、生成全错，只有把两层分开测才能定位。

### 8.2 一个真实的语料错误：施行日期写错了 20 年

测试用例 N09「预算法自什么时间起施行？」长期答不出来。查检索：top1 是法规文件头（已被 3.3 节的方法剔除），剔除后 top1 变成第一百零一条——还是答不出。

打开语料原文看：两版预算法第一百零一条都写着「本法自**1995年1月1日**施行」。查权威文本：2014 年修订的预算法应自 **2015 年 1 月 1 日**起施行。1995 是 1994 年原法的施行日期——说明下载的源页面把原法条文和修正说明混在了一起，第一百零一条取到了旧文本。

**修法**：按官方文本更正两版语料的第一百零一条，重建索引。

**这件事的价值不是修了个 bug，而是暴露了一条纪律**：RAG 系统的答案质量上限 = 语料质量，而**语料错误在检索指标上完全看不出来**（检索命中率 100%，答案就是错的）。所以政企项目里"知识库入库前的原文校验"必须是独立环节，不能靠检索指标兜底。这也是为什么本项目在 POC 报告里坚持保留"逐条人工可复核"的明细，而不是只报一个总分。

### 8.3 模型与参数实测：为什么留在 8B，为什么砍 top_k

| 配置 | 冷启动 | 热态单次 | 质量 |
|---|---|---|---|
| minicpm-v（8B，Q4，5.5GB） | 约 60s | 20~30s | 稳定，能守住"只依据资料" |
| MiniCPM5-2B（Q4，1.4GB） | 约 120s | 较慢 | 差：自行补充了资料里没有的原因（"已被实时推送至其他平台"） |

2B 更小却更慢（本次实测含加载），更关键的是**会自作主张补内容**——对"宁可少答不可错答"的政企场景是硬伤。所以默认保留 8B，2B 作为低配环境的备选并在文档里标注风险。

延迟优化的两个参数调整（都实测过）：`TOP_K` 5→3（少两条参考资料，预填充短一截，明显提速，答案质量无差别）、`MAX_TOKENS` 512→320（小模型容易写废话，压上限同时提速）。**结论写进 README**：M1 上 8B Q4 冷启动一次约 1 分钟，热态 20~30 秒——这是端侧的真实代价，也是"要不要为政企场景换更小模型"的决策依据。

## 9. POC 测试报告生成器：把售前动作产品化

`python -m app.benchmark` 跑一遍 `qa_set.json` 的 24 个预设用例（常规问答 / 版本对比 / 超纲拒答 / 操作辅助四类），自动产出客户视角的验收报告：通过率、答案命中率、拒答正确率、逐条明细。

设计要点：

- **`--no-llm` 模式**：只测检索和闸门（秒级、零依赖），用检索原文冒充回答来测命中率。价值是**把"检索层质量"和"生成层质量"解耦验证**——检索层 19/24 时不用等模型就知道瓶颈在哪层。
- **判分归一化**：答案关键词命中判定前先去空白——原文"30 分钟"和关键词"30分钟"差一个空格就被判错，这种假阴性会污染所有统计。
- **四类用例的配比**是刻意设计的：10 条常规 + 4 条版本对比 + 6 条超纲 + 4 条操作辅助——**超纲占四分之一**，因为客户验收时必拿"不存在的条款"来考你，这正是 7.1 说的问题。
- 这条命令本身就是 JD 里"POC、方案输出、价值包装"的产品化：过去手工整理 Excel 的动作，现在是一条命令。

## 11. 面试高频追问预演

**Q: 为什么不用 LangChain？**
A: 这个项目的检索链路自己写不到 200 行，逻辑全在自己手里（比如"排序用混合分、判档用纯语义分"这种自定义行为，框架里是隐藏实现）。引入框架的价值在编排复杂多源数据时，本项目的复杂度用不上，反而增加调试黑盒。

**Q: 检索不准怎么优化？按优先级说。**
A: 实测优先级：① 切分策略（本项目最大收益点，条款粒度直接决定引用能不能对上）→ ② 查询预处理（bge 的指令前缀）→ ③ 混合检索（救原词直问）→ ④ rerank 模型（bge-reranker，粗召回 20 条精排 5 条）→ ⑤ 换更大 embedding 模型。前三步零成本或低成本，先做完再考虑花钱的。

**Q: 拒答阈值怎么定的？**
A: 不是拍的。用 benchmark 在真实语料上跑正负例的相似度分布，正例 0.49~0.84、负例 0.43~0.59，重叠区交给闸二闸三。语料变了分布就变，阈值是**校准参数不是常量**。

**Q: 端侧跑大模型性能够吗？**
A: 实测环境 Apple M1 / 16GB。8B Q4（5.5GB）冷启动一次约 60 秒、热态单次 20~30 秒；2B Q4（1.4GB）体积小但实测更慢且会更爱自行补充资料外的内容，所以默认选 8B。政企制度问答是"查条文"场景不是流式聊天场景，20 秒在验收标准内可以接受。核心论点：**客户已有的办公电脑即可运行，不需要采购 GPU 服务器**，这是端侧方案的成本论据。真要提速，路径是减少参考资料条数（top_k 2~3）、压生成上限，而不是盲目换更小的模型。

**Q: 你的提示词调过几版？怎么知道哪版好？**
A: 三版，每版都有明确的失败现象驱动。第一版规则太严，8B 模型拿着正确条款也选择拒答（9 条误拒答）；对照实验证明是"拒答逃生通道"被滥用；第二版把拒答条件收紧到"资料与问题完全无关"，并解释表格竖线语义，误拒答消失。判断标准不是"感觉好不好"，是 POC 测试集的通过率与逐条明细。

**Q: 这个项目和你的工作什么关系？**
A: 需求来自多省交付复盘的真实问题（数据保密→端侧、多版本→时效管理、怕编造→三道闸、驻场依赖→操作辅助），我是把售前踩过的坑产品化成了工具，POC 报告生成器就是把售前交付动作写成了一条命令。
