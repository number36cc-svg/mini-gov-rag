# mini-gov-rag · 基于 MiniCPM 的端侧政企制度智能问答

> 完全本地运行的政企制度知识库问答系统：数据不出内网，一台普通笔记本即可运行。
> 针对"制度类"知识库的真实落地痛点做了三项专门设计：**版本时效管理、可追责拒答、一键 POC 报告**。

## 1. 背景与痛点

本项目的需求来源不是想象，而是多省政企客户**实施交付复盘中的真实问题**（已脱敏）：

- **数据保密**：财务类数据保密要求高，客户不支持远程提供完整业务数据——云端 API 方案在这类客户中天然不可行，端侧是唯一解
- **驻场依赖**：现场实施成本高、多项目并行人力紧张，客户日常操作问题（系统提示看不懂、操作不会做）长期依赖实施人员响应
- **机构差异**：不同机构记账规则、操作配置差异明显，标准模板无法通用，差异化知识散落在各项目组手里，没有可检索的沉淀
- **制度时效**：政策文件多版本并存，"以最新版为准"，修订后业务同步容易滞后

云端大模型问答方案另有三重障碍：数据出域合规风险、按 token 计费成本不可控、隔离网环境无法访问外部 API。端侧（本地）大模型 + 本地向量检索，是这类场景的天然解。

## 2. 与普通 RAG Demo 的区别

制度类知识库问答不是"把 RAG 跑起来"就完了。本项目针对四类真实落地问题做了专门设计：

| 真实痛点 | 本项目的解法 |
|---------|-------------|
| 政策文件多版本并存，"以最新版为准"，修订条款需同步业务 | **版本时效管理**：入库带版本号/生效日期，检索优先最新生效版，支持新旧条款对比问答 |
| 客户最怕 AI 编造——答错要担责，宁可查原文 | **可追责拒答**：置信度分级（依据充分/部分依据/无法回答），无依据明确拒答并指引人工渠道；相关度不足但不算明显无关时走**灰档**——不生成答案，只展示最相关条款原文（目的类口语问题不会"库里有却答不了"） |
| 系统提示模糊、操作问题长期依赖实施人员驻场响应 | **操作辅助场景**：报错/提示解读、操作指引，实施人员与客户自助排障 |
| 各机构业务规则差异大、差异化知识散落无沉淀 | **多机构差异化知识**：知识库按机构/场景组织，按单位检索对应规则，模板不能通用但知识可以 |
| 试点验收要有据可依，售前交付 POC 测试报告 | **一键 POC 报告**：预设测试问答对，自动生成客户视角的测试报告（命中率/延迟/拒答正确率/数据不出域声明/成本对比） |

## 3. 方案架构

```
┌─────────────┐   ┌──────────────┐   ┌───────────────┐
│  制度文档     │→ │ 文档切分/向量化 │→ │ 本地向量索引    │
│ (PDF/Word)  │   │ bge-small-zh │   │ (含版本/场景元数据)│
└─────────────┘   └──────────────┘   └───────┬───────┘
                                             │ 混合检索 top-k
                                             │ (语义+字面，优先最新生效版本)
┌─────────────┐   ┌──────────────┐   ┌───────▼───────┐
│  Web 界面    │← │  提示词组装    │← │  三道闸拒答 +   │
│ (Streamlit) │   │  + 置信度分级  │   │  引用溯源/版本标注│
└─────────────┘   └──────────────┘   └───────────────┘
         │               │
         │       ┌───────▼────────┐
         │       │ MiniCPM (本地)  │
         │       │ Ollama          │
         │       └────────────────┘
┌────────▼─────────────┐
│ POC 报告生成器        │
│ (测试集→客户交付物)    │
└──────────────────────┘
```

向量索引用 numpy 直接实现（千级切片毫秒级暴力检索），未引入向量数据库——取舍理由见技术文档 3.4 节。

## 5. 实测数据

完整逐条明细见 [reports/POC测试报告.md](reports/POC测试报告.md)（一键生成，可直接作为客户 POC 交付物）。

|------|------|---------|
| POC 用例通过率 | **24 / 25（96%）**，25 条分四类：常规 11 / 版本对比 4 / 操作辅助 4 / 应拒答 6 | MacBook Pro (Apple M1, 16GB) |
| **拒答正确率（超纲问题）** | **100%（6/6）**——政企场景的核心指标：答错要担责，宁可拒答 | 同上 |
| 端到端延迟 | 平均 9.6~20.9s / 空载热态单问 6s（**受宿主机负载影响显著**，容量规划须按最差负载，见报告"已知边界"） | 同上 |
| 版本覆盖正确率 | 100%（版本对比题引用同时覆盖新旧两版） | 同上 |
| 知识库规模 | 6 份文档 / 287 切片 × 512 维 / 索引 <1MB | 同上 |

**未通过的 1 条为版本多步对比题**：条款定位与版本比对逻辑正确，但 7.6B 小模型多步推理不稳定导致表述不完整——这恰好印证了"小模型做垂直场景要靠检索层兜底，不能指望模型自己推理"的工程判断，也是后续 rerank 与微调迭代的直接动机。

## 6. 端侧 vs 云端 API 成本对比

以 100 人规模客户、每人每天 20 次问答、每年 250 个工作日估算：

| 方案 | 首年成本估算 | 数据出域 | 隔离网可用 |
|------|------------|---------|-----------|
| 云端 API（按 token） | 约 0.6万–2万元/年（50 万次问答 × 单次约 1800 token，按主流国产模型定价浮动） | 是 | 否 |
| 本地端侧（一次性部署） | 普通办公本即可，API 费用 0，边际成本为零 | 否 | 是 |

> 端侧方案在数据合规场景下不是"降级替代"，而是**唯一可行解**。

## 快速开始

```bash
# 1. 安装依赖
pip install -r requirements.txt

# 2. 安装并拉取本地模型（需先安装 Ollama: https://ollama.com，详见 MODEL_SETUP.md）
ollama pull minicpm-v

# 3. 建立向量索引（把公开制度文档放入 data/docs/ 后执行）
python -m app.ingest

# 4. 启动问答服务
python -m uvicorn app.main:app --port 8000   # API 服务
streamlit run app/ui.py                      # Web 界面

# 5. 生成 POC 测试报告
python -m app.benchmark            # 完整测试（需模型）
python -m app.benchmark --no-llm   # 只测检索层（秒级，无需模型）
```
